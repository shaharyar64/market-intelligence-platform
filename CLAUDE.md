# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Market Intelligence Platform

Collect market data, enrich it with LLMs, serve it over an authenticated API, and present it as dashboards. The domains covered are beverage retail pricing (UAE/Bahrain), banking and digital brand health, EV, HoReCa, real estate (UAE and Saudi), food intelligence, and campaign analytics.

## Repository layout

Three independently built and deployed projects vendored side by side. There is **no shared git root** — each has its own `.github/workflows/`, `.gitignore` and Dockerfile. Nothing imports across directory boundaries; the only coupling is AWS infrastructure (S3 buckets, Postgres databases) and HTTP.

| Directory | What it is | Stack | Deploys as |
| --- | --- | --- | --- |
| `1-scraper-and-qc/` | Weekly beer/cider price scraper + LLM extraction + AI QC | Python, Playwright, Polars, LangChain/OpenAI | One-shot ECS Fargate task (EventBridge, Tuesdays 06:00 UTC) |
| `2-backend/` | API gateway + 13 FastAPI analytics microservices | FastAPI, SQLAlchemy, Postgres, Redis, Cognito | One ECR image + ECS service **per service** (arm64) |
| `3-frontend/` | Multi-dashboard UI | Next.js 16 App Router, React 19, Tailwind v4, TS | Standalone Next build → ECR (arm64) |

End-to-end data flow:

```
target sites ──► 1-scraper-and-qc ──► S3 (raw-data-prod) ──► cleaning.py ──► Postgres
                                                                               │
social APIs (Apify) ──► 2-backend/data_scraping_service ────────────────────►  │
                                                                               ▼
                 3-frontend ◄── gateway :8000 /api/v1/{service}/… ◄── FastAPI services
```

Branch conventions differ per project: `1-scraper-and-qc` deploys from `main`, `2-backend` and `3-frontend` deploy from `prod`.

## 1-scraper-and-qc

### Commands

All commands run **from `1-scraper-and-qc/`** — `sites/*.py` do `sys.path.insert(0, "..")` and every module imports flat (`import settings`, `from s3 import S3Client`).

```bash
python run_all_scrapers.py --list                       # available scraper names
python run_all_scrapers.py --date 2026-06-18 --extract-after
python run_all_scrapers.py --only citydrinks,gmp --concurrency 1
python sites/citydrinks.py --date 2026-06-18            # one site directly
python cleaning.py --date 2026-06-18                    # S3 extracts -> Postgres
python qc_agent.py --help                               # AI accuracy report
python generate_weekly_report.py --date 2026-06-18
```

`entrypoint.sh` is the production pipeline and the best reference for ordering: `run_all_scrapers.py --extract-after` → `cleaning.py` → `generate_weekly_report.py` → `notify_discord.py`. The weekly report is skipped if cleaning fails; Discord is notified either way.

### Architecture

Each site collector is a standalone script in `sites/`, registered in two dicts in `run_all_scrapers.py` — `SCRAPERS` (name → script + args) and `EXTRACT_SITE_BY_SCRAPER` (scraper name → the site key `extract_from_html_manifests.py` uses). Adding a site means touching both, plus the `SOURCES` list in `cleaning.py` and `PLATFORM_TO_CURRENCY` in `data_extractor.py`.

Two collection styles coexist: API-backed sites use `requests` directly (see `sites/citydrinks.py`), browser-backed sites use the shared Playwright engine in `scraper.py`, configured globally by `settings.py`. Collectors write **raw** payloads to S3 (`raw-data-prod`, prefixed per site) and never parse — parsing is a separate pass so extraction can be re-run without re-scraping.

`data_extractor.py` turns raw HTML/JSON into the product schema using an LLM (`langchain_openai`), with deterministic helpers for brand / sub-type / quantity / pack-format normalization. `qc_agent.py` imports those same helpers to grade extracted rows against the raw S3 source and reports product- and field-level accuracy. The product field contract (brand, type, quantity, units, pack_format, prices, discount %, availability, top-10 / first-page flags) and the fixed USD multipliers (AED 0.272, BHD 2.648) are documented in `README.md` and encoded in `CURRENCY_TO_USD`.

Sub-type classification is driven by CSVs, not code: `sub_type_rules.csv` (curated) and `discovered_sub_type_rules.csv` (generated by `generate_discovered_sub_type_rules.py`).

Credentials: `db.py` pulls the Postgres password from Secrets Manager (`SECRET_NAME`, an auto-rotated `rds!db-…` secret) — never from `.env`. Login state for gated sites lives in `sessions/` and `cookies/`, generated by `generate_session.py` and baked into the image, so an expired session requires a rebuild (see `deploy/README.md`).

## 2-backend

### Commands

Everything runs **from `2-backend/`** with module paths, because `shared` is imported as a top-level package (`PYTHONPATH=/app` in the image).

```bash
pip install -r requirements.txt                    # all services, local dev
honcho -f Procfile.dev start                       # every service + gateway
honcho -f Procfile.dev start gateway food          # just what you need
make run-dev                                       # == honcho -f Procfile.dev start
python -m uvicorn gateway.app.main:app --reload --port 8000
python -m uvicorn services.food_intelligence_service.app.main:app --reload --port 8008

pytest                                             # only food + trends (see pytest.ini)
pytest gateway/tests                               # gateway tests are NOT in testpaths
pytest services/ceer_campaign_service/tests        # nor are ceer's
pytest services/food_intelligence_service/tests/enrichment/test_pipeline.py::test_name

docker compose -f .devops/docker-compose.yml up --build    # from 2-backend/
```

`pytest.ini` sets `testpaths` to the food and trends services only. Other suites exist (`gateway/tests`, `ceer_campaign_service/tests`) and must be named explicitly or they silently don't run.

### Gateway and authorization

`gateway/app/main.py` is a single catch-all proxy: `/api/v1/{service}/{path}` looks `service` up in `SERVICE_MAP` (URL segment → upstream host) and `SERVICE_NAME_MAP` (URL segment → the human service name as stored in the DB). Both dicts carry hyphen and underscore aliases for the same target.

Each proxied request does a DB round trip before forwarding: resolve the Cognito `sub` to a `users` row, read that user's grants from `user_services JOIN services`, then `authorize_service_access`. Membership of the Cognito group `Admins` bypasses the check entirely (`core/authorization.py`). So **a new service is unreachable until a row exists in the `services` table and is linked to users** — a code-only change returns 403.

`utils/proxy.py` relays upstream responses as they arrive rather than buffering. This is deliberate and load-bearing: the assistant endpoints answer over SSE, and buffering delivered every event in one burst at the end. The `httpx.AsyncClient` is intentionally not closed inside `forward_request` — it owns the socket the stream is still reading from, and is closed in the relay iterator's `finally`.

### Two databases, two migration runners

- **`DB_ADMIN`** ("dashboards") holds auth/admin: `users`, `services`, `user_services`, `products`. Migrations live in `gateway/migrations/`, applied with `python gateway/migrations/run_migration.py <file.sql>`.
- **`DB_NAME`** ("raw_data") holds all service data (`beer_pricing_analysis.*`, `food_intel.*`, scraped social tables). Migrations live in `shared/migrations/`, applied with its own `shared/migrations/run_migration.py`.

The two runners are near-identical and point at different databases — picking the wrong one is the easy mistake. Both resolve credentials through Secrets Manager (`SECRET_NAME`), with `POSTGRES_DSN` as a local-dev shortcut.

### Service structure and shared code

Every service follows the same shape: `app/main.py` (FastAPI app + lifespan) → `app/api/v1/*.py` (routers, mounted at `/api/v1`) → `app/services/*.py` (SQL and business logic) → `app/models/*.py` (Pydantic). Each exposes `GET /api/v1/health`, which the gateway's public `/services/health` polls.

`shared/` is the only cross-service code — `database.py` (SQLAlchemy pooling, Polars reads, credential self-healing on auth errors), `redis.py`, `cache.py`, `logger.py`, `exceptions.py`. It deliberately reads config from env vars directly instead of importing the gateway's `Settings`, so each service image can ship `shared/` plus its own directory and nothing else.

Most services are read-only SQL over Postgres. `food_intelligence_service` is the exception and worth reading its `README.md` before touching: it adds an offline CLI write path (`python -m services.food_intelligence_service.app.enrichment.run --platforms instagram`) running a 7-node LangGraph analysis graph whose nodes are required to stay independent — a caption-less post must still get full visual analysis, and an image-less post full text analysis.

### Builds

`requirements.txt` is a local-dev superset of `requirements-base.txt` + `requirements-food.txt` + `requirements-dev.txt`. Images install only base plus the one extras file they need: `.devops/Dockerfile` takes `SERVICE_DIR`, `EXTRA_REQUIREMENTS_FILE` and `INSTALL_BUILD_TOOLS` build args and copies only `shared/` and that one service, so a commit to one service leaves other images' digests unchanged. `.github/workflows/prod.yaml` holds the authoritative `name|dir|requirements|build_tools` table and rebuilds only services whose directory — or `shared/`, or the requirements files — changed. Everything is pinned to `linux/arm64` (Graviton).

### Adding a service — the full checklist

1. `services/<name>_service/` following the structure above, with a `/api/v1/health` route.
2. `<NAME>_SERVICE_URL` in `gateway/app/core/config.py` on a free port.
3. Entries in **both** `SERVICE_MAP` and `SERVICE_NAME_MAP` in `gateway/app/main.py`.
4. A line in **both** `Procfile.dev` and `Procfile.prod`.
5. A row in the `ALL` table in `.github/workflows/prod.yaml`, and a service in `.devops/docker-compose.yml`.
6. A migration inserting it into the `services` table in `DB_ADMIN` — see `gateway/migrations/006_add_ceer_campaign_service.sql`.

## 3-frontend

### Commands

```bash
npm run dev            # Next dev server on :3000
npm run build          # standalone output
npm run lint           # eslint (flat config, next/core-web-vitals)
node --test "lib/*.test.mjs"                  # the whole suite
node --test lib/dashboardUi.test.mjs          # one file
```

There is no `test` script in `package.json`. Tests are plain `node:test` files (`lib/*.test.mjs`) that import `.ts` sources directly and rely on Node's native TypeScript type stripping, so they need a recent Node (verified on v24). Pass the glob in quotes — the directory form `node --test lib/` fails with MODULE_NOT_FOUND.

Some of these tests assert against the **source text** of components via regex (e.g. `ceerCampaign.charts.test.mjs` reads chart files and matches on accessibility labels). Editing a component's JSX can therefore break a `lib/` test without any logic changing.

`NEXT_PUBLIC_API_URL` is required at import time — `lib/apiClient.ts` and `lib/authSession.ts` both throw at module load when it is missing, so the app will not boot without it.

### Architecture

App Router with two route groups: `app/(auth)/` for the login/password flows and `app/(dashboard)/<service>/` for each dashboard. Dashboard route names mirror the gateway's `SERVICE_MAP` keys, with `pricing` → `beer` the one that doesn't.

Auth is split-token: the access token lives **in memory only** (`lib/authSession.ts`), the refresh token in an httpOnly cookie set by the gateway. `lib/apiClient.ts` wraps every call — it refreshes when no token is held, retries once on a 401, and hard-redirects to `/login` on failure. `refreshAccessToken` deduplicates concurrent refreshes through a single `activeRefresh` promise. Use `apiFetch` for gateway calls, never a bare `fetch`.

Each dashboard gets a typed API module in `lib/` (`foodIntelligence.ts`, `bankBrandHealth.ts`, `pricingAnalysis.ts`, …) that owns its endpoints and response types; components consume those, usually through `lib/useAsyncResource.ts`. Chart palettes are per-dashboard modules too (`foodPalette.ts`, `pricingBrandColors.ts`, `bankColors.ts`, `sequentialScale.ts`) — reuse the existing one rather than hard-coding colors. `lib/navigation.ts` defines the sidebar and supports optional per-item `roles`.

`app/api/*/chat/route.ts` (bank-brand-health, digital-brand-health, saudi-real-estate, uae-bank-brand-health) are explicitly marked stopgaps in their own comments: they proxy to a hard-coded `http://localhost:5003/chat` instead of going through the gateway. Don't copy them as the pattern for new endpoints.

`next.config.ts` sets `output: "standalone"` (the Docker build depends on it) and currently allows remote images from any hostname.
