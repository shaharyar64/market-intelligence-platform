# Trends Pipeline — Data Lineage Reference

Every data artifact the trend system produces: what it is, what generates it,
from what input, and how to regenerate it. Code lives in
`services/food_intelligence_service/app/trends/` (pipeline),
`app/etl/` (ingest), `app/services/trend_service.py` + `app/api/v1/trends.py` (read side).

```
Mongo (local dumps)                POSTGRES (RDS)                        S3
trends_universal_etl               raw_data db                           trends-media-bucket
─────────────────────              ────────────────────────────          ──────────────────
community_posts   ──┐              public.community_posts   ◄─┐          {source}/{platform}/
raw_posts (B/I)   ──┼── ETL ─────► food_intel.post_embedding │            {post_id}/{n}.jpg
                    │              food_intel.trends         │
Azure blobs ────────┴──────────────────────── media ─────────┴─────────►
```

---

## 1 · `public.community_posts` (Postgres) — the post corpus

| | |
|---|---|
| Generated by | `app/etl/migrate_community_posts.py` |
| Input | Mongo `trends_universal_etl.community_posts` (source=Community) or `raw_posts` (source=Brand/Influencer), local instance |
| One row per | post (PK `platform, post_id`; Instagram shortcode / TikTok video id extracted from `post_url`) |
| Key fields | caption, hashtags[], mentions[], engagement counts, `source` (community/brand/influencer), `cohort` tag, `posted_at`, `media_keys[]`, `media_status` |
| Field cleaning | `pub_date` two formats normalised; hashtags CSV→array; `search_keyword` stringified-list parsed; `Undefined`→NULL; age/gender dropped (fabricated upstream) |
| Regenerate | `python -m ...app.etl.migrate_community_posts --source Brand --since 2026-04-14 --limit 0 --workers 24` (idempotent upsert; `--retry-failed` re-attempts failed media) |

## 2 · S3 media — `trends-media-bucket`

| | |
|---|---|
| Generated by | same ETL run (unless `--skip-media`) |
| Input | Azure blob URLs in each Mongo doc — only the public `trendsapp` container is reachable; `gussocialcap16835` (newest ~135K community posts) needs credentials we don't have |
| Key | `{source}/{platform}/{post_id}/{index}.{ext}` — index = position in the source record, not a completeness claim; `media_count` on the row is authoritative |
| Excluded | `.mp4` videos (cover image suffices for analysis) |

## 3 · `food_intel.post_embedding` (Postgres, pgvector)

| | |
|---|---|
| Generated by | pipeline stage **embed** (`embedder.py`) |
| Input | `caption + #hashtags` (6,000-char cap) per community_posts row with a caption |
| Model | OpenAI `text-embedding-3-large`, `dimensions=1024`; `model` column = `text-embedding-3-large@1024` so future models coexist |
| One row per | (platform, post_id, model) — run-independent, shared by all runs and the future AI assistant (HNSW cosine index) |
| Incremental | anti-join means only never-embedded posts are sent; re-runs cost nothing |

## 4 · Sentiment labels — `.trend_cache/{cohort}/sentiment.json`

| | |
|---|---|
| Generated by | stage **sentiment** (`sentiment.py`) |
| Input | **community** captions only (consumer-voice metric; brand/influencer excluded by design) |
| Model | `OPENAI_MODEL` (gpt-4o-mini), 20 captions/call, JSON mode, invalid→`neutral` |
| Shape | `{"platform:post_id": "positive|neutral|negative"}` — labels only; the 0..1 trend sentiment is computed later as share-of-positive |

## 5 · Run cache — `.trend_cache/{cohort}/run_{run_id}.json` + `bertopic_{run_id}`

| | |
|---|---|
| Generated by | stages **cluster / name / group / assign** (`run.py` saves after each) |
| Contents | cluster labels + c-TF-IDF keywords + per-post centrality; named-trend results; umbrella partition; brand/influencer topic assignments; run provenance (embed/naming model, prompt version, cluster params) |
| BERTopic model | fitted model saved beside it — used by **assign** (`transform` on new posts) and any future train-once/predict-weekly cadence |
| Purpose | resumability: any stage can re-run without repeating earlier LLM spend; crash loses at most one in-flight batch |

## 6 · `food_intel.trends` (Postgres) — the final trend objects

Written by stage **metrics** (`metrics.py` computes, `store.upsert_trends` writes; `delete_run(run_id)` first, so a rerun replaces only its own run). One row per trend, `level` = micro or umbrella.

| Field | Generated how |
|---|---|
| `trend_id` | slugified LLM name + run suffix (`cake-creations--all-v2`) |
| `name`, `narrative.summary/related_themes/product_entities` | **LLM (stage name)** — gpt-4o over top-25 captions by centrality×engagement + top hashtags + c-TF-IDF keywords; coherence gate (`is_coherent`, ≥15 posts, ≥5 authors) discards bad clusters |
| umbrella rows + `parent_trend_id` | **LLM (stage group)** — one call over micro summaries; partition repaired in code (strays → flagged Misc) |
| `quadrant, volume_index, growth_index` | **math** — percentile ranks within level; median-split quadrant matrix |
| `sentiment` | positive ÷ labeled community members |
| `metrics` jsonb | volume_raw (90d), growth_pct (8w vs prior 8w, clamped), engagement_total, platform_mix, **source_mix** (community/brand/influencer counts via stage assign), as_of = max posted_at |
| `timeline` jsonb | ISO-week buckets: posts, engagement, unique authors |
| `example_posts` jsonb | `{top: [6 by engagement], by_source: {community/brand/influencer: 3 each}}` with S3 media_key |
| `member_posts` jsonb | every (platform, post_id, source) — makes any number reproducible from raw rows |
| `narrative.opportunity_summary` | **LLM (stage interpret)** — gpt-4o given the *computed* metrics; may only reference supplied figures |

## 7 · API payloads (not stored — derived per request)

`trend_service.py`: serves the **newest run** only. Derived at read time: sparkline
(last 7 timeline weeks), month-mode re-ranking (trailing 4w vs prior 4w from
timelines), movers + KPI deltas (vs previous run, matched on name slug),
Brands-Tracked KPI (distinct brand authors), presigned S3 image URLs (24 h),
`search_timeline: null` (no food search-interest source connected yet).

## Running it

All configuration (models, API keys, DSN, `TREND_NAMING_MODEL=gpt-4o`) comes from
`.env` — commands never carry inline settings. From the repo root:

```bash
# schema (idempotent, one-time)
python shared/migrations/run_migration.py shared/migrations/007_create_food_trends.sql

# ingest a source (whenever new scraped data lands)
python -m services.food_intelligence_service.app.etl.migrate_community_posts --source Influencer --since 2026-04-14

# full pipeline run — a fresh run gets a new --run-id; all stages by default
python -m services.food_intelligence_service.app.trends.run --cohort all --run-id all-v3

# partial re-run of an existing run (cheap — reuses cached cluster/name state)
python -m services.food_intelligence_service.app.trends.run --cohort all --run-id all-v3 --stages metrics,interpret

# tests
pytest services/food_intelligence_service/tests/trends/ -q
```

Stage order matters: `cluster` needs embeddings; `name` needs cluster; `group`/`assign`
need name/cluster; `metrics` folds in assign if present; `interpret` reads what
metrics wrote. Trends are **discovered** from community posts only; brand/influencer
posts are **assigned** into them and change counts, never topics.
